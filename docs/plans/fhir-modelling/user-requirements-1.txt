  <!-- 1. PRIMARY OBJECTIVE                                             -->
  <!-- ================================================================ -->

  <objective>

    Extend the existing openEHR Modelling Assistant into a multi-standard clinical
    modelling platform.

    The platform must support at least two independent modelling domains:

    1. openEHR
    2. HL7 FHIR

    The existing openEHR functionality must remain intact.

    FHIR must be implemented as a separate standards provider/module rather than by
    contaminating openEHR-specific code with FHIR logic.

    The resulting conceptual architecture should be:

    Clinical Modelling Platform
        |
        +-- Common Platform Services

      - inspect artifact

      - validate artifact
      - diff artifact
      - resolve dependencies
      - resolve terminology
      - save artifact
      - retrieve artifact
      - publish artifact
      - obtain provenance

  <!-- 3. FHIR VERSION SUPPORT                                          -->
  <!-- ================================================================ -->

  <fhir-versioning>

    Support explicit FHIR version selection.

    Initial architecture must accommodate:

    - R4
    - R4B
    - R5

    Do not silently mix artifacts from different FHIR releases.

    Every FHIR workspace/project must declare its FHIR version.

    Every package dependency must be checked for compatibility with the configured
    FHIR version.

    Validation must occur against the configured version.

  </fhir-versioning>

  <!-- ================================================================ -->

  <repositories>

    Support independent repository configuration.

    Example:

    Project: Uganda Maternal Health

      openEHR:
        repository: clinical-models-openehr

      FHIR:
        repository: clinical-models-fhir

        repository: clinical-model-mappings

    Repository configuration must support:

    <repository-properties>
      <property>provider/standard</property>
      <property>repository URL</property>
      <property>branch</property>
      <property>artifact root path</property>
      <property>authentication configuration</property>
      <property>read/write permissions</property>
    </repository-properties>

    Reuse the existing GitHub/GitLab/filesystem repository infrastructure where possible.

  </repositories>

  <!-- 6. FHIR SOURCE-OF-TRUTH MODEL                                    -->
  <!-- ================================================================ -->

  <source-of-truth>

    Treat source-controlled FHIR artifacts as the engineering source of truth.

    The Implementation Guide server is a publication/governance/distribution destination.

    A runtime FHIR server is a deployment/testing/runtime destination.

    These three concepts MUST NOT be treated as identical:

      1. Git repository
      2. Implementation Guide server
      3. Runtime FHIR server

    Maintain separate connection types for each.

  </source-of-truth>

    Support:

    - FSH
    - FHIR JSON
    - FHIR XML where practical

    Preferred authoring pipeline:

      requirements
          ->
      modelling analysis
          ->
      FSH
          ->

          ->
      StructureDefinition/resources
          ->
      FHIR validation
          ->
      review
          ->
      Git
          ->

    Generated JSON must not replace FSH source unless the project explicitly chooses
    JSON-first authoring.

  </fhir-authoring>

  <!-- 11. MII SUPPORT                                                  -->
  <!-- ================================================================ -->

  <mii>

    Add MII as a configurable FHIR knowledge source.

    The agent should be able to inspect installed/configured MII packages and determine
    whether an existing MII profile, extension, ValueSet or CodeSystem satisfies a
    modelling requirement.

    Example request:

      "Create a laboratory result profile for a German research project using MII
       wherever possible."

    Expected behaviour:

      1. determine configured FHIR version;
      2. inspect project dependencies;
      3. search configured MII packages;
      4. identify potentially reusable profiles;
      5. inspect their constraints;
      6. inspect terminology bindings;
      7. prefer reuse or derivation;
      8. create new constraints only when necessary;
      9. record the package/version from which the artifact derives.

    Never copy an MII artifact and silently claim it is locally authored.

    Preserve provenance.

  </mii>

  <!-- 13. REUSE-FIRST POLICY                                           -->
  <!-- ================================================================ -->

  <reuse-policy>

    Implement the following default principles:

    <rule>Prefer reuse over creation.</rule>

    <rule>Prefer deriving from an applicable profile over duplicating it.</rule>

    <rule>Prefer standard FHIR elements over extensions.</rule>

    <rule>Prefer existing standard extensions over creating new extensions.</rule>

    <rule>Prefer authoritative terminology artifacts over locally invented code lists.</rule>

    <rule>Do not create duplicate profiles solely because names differ.</rule>

    <rule>Inspect semantics and constraints before determining equivalence.</rule>

    <rule>Do not automatically treat two artifacts as equivalent merely because they use the same FHIR resource.</rule>

  </reuse-policy>

  <!-- ================================================================ -->

      source artifacts
          ->
      dependency resolution
          ->
      SUSHI
          ->
      generated FHIR resources
          ->
      FHIR validation
          ->
      IG build
          ->
      publication package
          ->
      IG server

    Publication must record:

    - commit SHA
    - branch
    - package versions
    - FHIR version
    - build timestamp
    - validator result
    - publisher result
    - destination
    - artifact version

    Failed validation must not be represented as successful publication.

  </publication>
