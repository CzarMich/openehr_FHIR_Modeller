# Future visual modeller

A visual editor can use the domain services behind an authenticated application API. Keep HTTP/UI models in adapters and reuse `ModelRepository`, terminology, validation, traceability and governance services. MCP should remain one interface, not the storage or modelling domain.

Prepare selection of projects and configured CKMs, artifact history/diffs, requirement links, explicit value-set bindings, validation scope, unresolved decisions and human review. Preserve provider-neutral revisions and optimistic concurrency. Never display a draft structural check as deployment approval. A future editor can use the native ADL 2/OPT 2 engine and must integrate qualified validation and trusted user/role services before clinical release. The current browser offers model browsing and human review through a versioned review API; visual editing and the general modelling REST API remain separate work.

For an existing visual modeller, see [Archetype Designer integration](ARCHETYPE_DESIGNER_INTEGRATION.md). It documents GitHub-based collaboration and the current file exchange path, with Git synchronization implemented and hosted Designer account/format acceptance still to verify.
