Clinical data handling: read-only sources

Clinical databases are strictly read-only. Reviewed vendor capture and file sources feed private processing. FHIR delivery uses a separately authorised HTTP API. Uploaded records stay outside the chat and model registry. Storage encryption and retention are managed by your operator.

Each pin requires canonical, exact version and SHA-256. Use an empty list only when no external terminology snapshots are dependencies; embedded rule dictionaries are already pinned in the mapping. Do not invent versions or hashes.

Kafka topic intake

Consume a reviewed topic into durable private intake. Broker offsets are committed only after private records and checkpoints are saved. Topic data is never written. Mapping and exact model confirmation are separate.

5. Run or configure a channel

                    
                    

                        Continuous channel
                        

                            A channel pins one confirmed mapping version and polls stable files. It never changes the
                            mapping automatically. A restart requires an explicit start. Inputs are never deleted or
                            modified.
                        

                        
                        
                        

                            Strict FIFO blocks on a missing Patient or Encounter. Supply prerequisite registrations on a
                            separate channel, or choose ready-order processing. Files enter the queue by modification
                            time, then filename; committed queue order survives restart. Concurrent completion order is
                            not guaranteed.
                        

                        
                        
                        

                            The installation admits at most two workers. These are .NET managed-heap limits, not total
                            process RAM. Pending inputs stay on disk, subject to storage limits.
